# Release v0.4.0 — Login hardening & status-badge CSS drift fix

**Date:** 2026-08-02
**Git tag:** `v0.4.0`
**Baseline commit:** `f1d7696`
**DoD met:** yes

---

## Summary

Bugfix milestone on top of `v0.3.0`'s real Jakarta Security RBAC. Two concrete defects, both
introduced by the `v0.3.0` migration and both now root-caused + regression-guarded:

1. **Double password verification per login.** `v0.3.0` layered real container auth
   (`UserIdentityStore` + `LoginAuthenticationMechanism` + `HttpServletRequest.login()`) on top
   of the pre-existing hand-rolled `LoginUseCase.login()` path but never removed the old path.
   `LoginBean.login()` therefore ran the full domain check twice on every successful login: two
   Argon2id comparisons (deliberately CPU-expensive) and two persists, plus two sources of truth
   about "who is logged in". Fix: the container is the single credential-verification point — a
   cheap read-only `canLogin()` pre-flight (no hashing, still no email-existence leak) before
   `request.login()`, then `establishSession()` (no re-check) after. Guarded by a new
   `LoginBeanTest` whose central assertion fails if the double path returns.
2. **Status-badge CSS drift.** `OrderStatus` had grown from 3 values (OPEN/CONFIRMED/CANCELLED)
   to 7 (PENDING/CONFIRMED/PROCESSING/SHIPPED/DELIVERED/CANCELLED/REFUNDED) but the CSS still
   mirrored the old set: `PROCESSING`/`SHIPPED`/`DELIVERED`/`REFUNDED` badges rendered with no
   color and the dead `--color-status-open` / `.status-OPEN` lingered. Fix: tokens + rules
   aligned to all three status enums (existing primitives only, no new hex) and a new
   `StatusBadgeCssCoverageTest` in the `web` module that fails the build if any enum constant
   lacks CSS coverage, or vice versa, or a token is orphaned — the first test of the `web` module.

## In scope (delivered)

- [x] `LoginBean` single-verification flow: `findByEmail().canLogin()` pre-flight (locked/inactive
      message, no hash, no email-existence leak) → `request.login()` (the one Argon2id check) →
      `establishSession()` (no password check) → `changeSessionId()`
- [x] `LoginBeanTest` (new): 5 cases — success (exactly-one auth), unknown email, wrong password,
      locked account short-circuit, logout
- [x] `LoginUseCase.login()` Javadoc now states the web layer must not call it (regression guard
      documented on the port itself)
- [x] `design-tokens.css`: added `--color-status-processing/shipped/delivered/refunded`, removed
      dead `--color-status-open`, corrected the status enum comment + header changelog
- [x] `base.css`: `.status-*` rules aligned to the 7 `OrderStatus` values, dead `.status-OPEN`
      removed
- [x] `StatusBadgeCssCoverageTest` (web module): enum↔CSS↔token coverage, both directions
- [x] `web/pom.xml`: first test dependencies (`junit-jupiter`, `assertj-core`) + surefire 3.2.5
      (Maven default 2.12.4 cannot run JUnit 5)
- [x] Docs: lessons #9 + #10, `docs/design-system.md` changelog entry (Strict-tier), README
      current state
- [x] CI green on `main` (unit + ArchUnit + WAR, then Testcontainers integration tests)

## Lessons promoted

- #9 When real container auth is layered over a hand-rolled auth path, remove the old path in the
  same change set — otherwise every login runs the domain check twice (2× Argon2id, 2× save) and
  two "who is logged in" sources of truth coexist.
- #10 Design-code drift (enum ↔ CSS tokens) needs an automated coverage guard, not just a
  documented convention.
