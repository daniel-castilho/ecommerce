## Summary

Closes the last two outstanding reviews-ratings items from the epic backlog: the **author-facing
"my reviews" screen** and **moderation email notifications**. Customers now have a self-service
page listing every review they wrote across all moderation states (with product links, statuses and
a hide-own-review action), and approve/reject now notify the author by email — reusing the
order-checkout transactional outbox, so no module dependency was added and no SMTP work happens on
the moderation thread.

## In scope (delivered)

- **Customer "My Reviews" screen** at `/product-reviews/my-reviews.xhtml`:
  - New `ListMyReviewsUseCase` + `findByAuthor`/`countByAuthor` on `ReviewRepositoryPort`
    (newest first, paginated, all statuses).
  - `MyReviewsBean` (thin JSF adapter) resolves product names/slugs through product-catalog's
    public `ProductRepositoryPort`; **hide-own-review** action for APPROVED reviews
    (previously the `HideOwnReviewUseCase` was unreachable from any UI).
  - Table with product link, review title/body, rating, status badge (`my:statusBadge`),
    rejection reason for REJECTED, formatted date, pagination; **My Reviews** link added to the
    profile account bar.
- **Moderation notifications** (approve/reject):
  - New `ReviewNotificationPort` in product-reviews' domain (no foreign/framework imports;
    ArchUnit-clean) and `ReviewNotificationEmailAdapter`, which depends **only** on
    `NotificationDeliveryLogPort` (order-checkout) + `FindUserUseCase` (user-account) and claims
    idempotent `REVIEW_APPROVED:{reviewId}` / `REVIEW_REJECTED:{reviewId}` outbox rows with a
    rendered snapshot (subject + text + HTML body) inside the moderation transaction.
  - `ReviewNotificationMessageBuilder` mirrors the order email HTML layout (design-token hex
    values, HTML-escaped author/reason strings).
  - Wired into `ReviewApplicationService.approve()` / `reject()`; respects
    `UserProfile.notificationsEnabled`; best-effort — moderation never fails on notification
    delivery; the existing 5 s poller dispatches the rows (no dispatcher change).
- **Tests**: service tests for `listMine` + notify-on-approve/reject; `MyReviewsBeanTest`;
  `ReviewNotificationMessageBuilderTest` (escaping); `ReviewNotificationEmailAdapterTest`
  (claim/disabled/duplicate/author-not-found); repository IT covering `findByAuthor`/`countByAuthor`
  pagination and exclusion of other authors.

## Out of scope / explicit debt

  transition (kept as backlog debt).
- Review media, helpfulness votes, vendor replies, AI moderation.
- Rating on catalog cards / search; blocking non-purchasers (product decision, badge-only today).

## Lessons promoted

- **#43 (2026-08-13):** the transactional notification outbox is reusable across modules: any
  module can depend *only* on `NotificationDeliveryLogPort` and enqueue idempotent rows — the
  poller dispatches every due row regardless of `eventType`, so keep event-type prefixes specific
  (`ORDER_CONFIRMED`, `REVIEW_APPROVED`, …) in the idempotency keys. Cross-module notification
  without touching the owning module, and with no SMTP on the request thread.
