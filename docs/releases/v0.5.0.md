# Release v0.5.0 — Real admin-dashboard metrics & JASPI-compliant programmatic login

**Date:** 2026-08-02
**Git tag:** `v0.5.0`
**Baseline commit:** `c20e073` (tag `v0.4.0`)
**DoD met:** yes

---

## Summary

Two milestones in one: (1) the `admin-dashboard` epic's **S2 — real metrics** now renders
live KPIs on `/admin-dashboard/dashboard.xhtml` (no more hardcoded zeroes), and (2) the login
bug that blocked the whole smoke path is fixed at its root — on Open Liberty, programmatic login
had to stop using `HttpServletRequest.login()` (forbidden while a JASPI mechanism is active) and
switch to `SecurityContext.authenticate(...)`. Both were validated end-to-end on the running
server: admin login → dashboard shows values that match the database row-for-row.

## In scope (delivered)

- [x] **Real dashboard metrics (S2).** `DashboardBean` + `dashboard.xhtml` (new, styled with
      existing tokens only) render: total users / products / orders, new customers today & this
      month, orders today & this month, revenue today & this month, average order value, and an
      orders-by-status breakdown.
- [x] **`CountUsersUseCase`** (user-account): `countAll()`, `countRegisteredToday()`,
      `countRegisteredThisMonth()` — backed by `UserRepositoryPort` + one `SELECT COUNT` each.
- [x] **`AdminOrderMetricsUseCase`** (order-checkout): `countAllOrders()` +
      `getOrderMetrics()` — `revenueSince`, `countCreatedSince`, `countByStatus` on
      `OrderRepositoryPort`; `OrderMetrics` record lives in the `order-checkout` domain model
      (ArchUnit forbids classes in `domain.port`, so it sits in `domain.model`).
- [x] `DashboardMetricsService` composes the other modules' input ports only (no business rules,
      no adapter imports — hexagonal rules intact, `OrderHexagonalArchitectureTest` green).
- [x] **Login fix (root cause).** `LoginBean.login()` now calls
      `securityContext.authenticate(request, response, AuthenticationParameters.withParams()
      .credential(new UsernamePasswordCredential(email, password)))` instead of
      `request.login()`, which Open Liberty rejects with "The login method may not be invoked
      while JASPI authentication is active". Failure still renders the inline message; success
      persists the caller via `@AutoApplySession` + `request.changeSessionId()`, then
      `establishSession()`. `LoginBeanTest` rewritten for the new flow (5 cases green).
- [x] **LTPA keys password.** `<ltpa keysPassword="keystore-password-dev"/>` in
      `web/src/main/liberty/config/server.xml` — Open Liberty 26.0.0.4+ removed the default LTPA
      keys password (CVE-2025-14917), so without it the LTPA service failed (`CWWKS4118E`) and
      container login broke. Dev DB migrated to the current schema (V10–V15 applied + registered
      in `flyway_schema_history`, per repo convention).
- [x] Debug instrumentation removed; deployed `server.xml` restored to the source (temp trace
      dropped); server restarted clean (LTPA ready `CWWKS4105I`, app started `CWWKZ0001I`).

Smoke path (validated 2026-08-02 on the running Open Liberty):

1. Login `qa.admin@loja.com` / `SmokeTest@123` on `/web/user-account/login.xhtml` → 302 to

  `<ltpa keysPassword>` and regenerate `ltpa.keys`.
