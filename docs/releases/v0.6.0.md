# Release v0.6.0 — Admin back-office management (orders, products, customers, refunds) + refund workflow

**Date:** 2026-08-03
**Git tag:** `v0.6.0`
**Baseline commit:** `e24f9e4` (tag `v0.5.0`)
**DoD met:** yes

---

## Summary

Turns the admin-dashboard from a read-only KPI screen into a working back-office: full
management UIs for **orders** (list + detail with status update), **products** (create/edit +
archive/reactivate with audit trail), **customers** (list, detail, block/unblock with audit
trail) and **refunds** (paginated list with status filter, detail page with approve/reject).
The order-checkout module gains the **refund request workflow** domain (PENDING → APPROVED →
PROCESSED / REJECTED), a `PaymentGatewayPort` with a mock adapter, and a `V16` migration.
product-catalog gains archive/reactivate with `ProductArchivedEvent`. The dashboard's broken
confirm modal is fixed (taglib path bug — see lessons #13). All touched modules are unit/IT
green; smoke path validated on the running server.

## In scope (delivered)

- [x] **Refund workflow (order-checkout).** `RefundRequest` aggregate (id, orderId, amount,
      reason, status, rejectionReason, timestamps), `RefundStatus` enum, `request/approve/reject/
      markAsProcessed` domain rules, `RefundRequestRepositoryPort` + JPA adapter + entity,
      `RefundManagementUseCase` + `RefundApplicationService`, `PaymentGatewayPort` with a
      mock adapter (no provider integration yet), Flyway `V16__refund_request_workflow.sql`.
      45 order-checkout unit tests green.
- [x] **Refunds UI (admin-dashboard S17–S19).** `RefundManagementBean` (`@ViewScoped`,
      `@RolesAllowed("ADMIN")`): paginated list (20/page), `RefundStatus` filter, previous/next;
      `RefundDetailBean`: detail card + Approve (confirm) and Reject (required reason);
      `refunds/list.xhtml` + `refunds/detail.xhtml`; dashboard card linking to the list.
- [x] **Order & product management UI (admin-dashboard S6–S7, S10–S13).** `OrderManagementBean`
      (list + filters + status update), `AdminOrderDetailBean` (order detail), `ProductManagementBean`,
      `ProductCreateBean`, `ProductEditBean` (image management), `CreateProductForAdminService`,
      `GetOrderDetailsService`, plus admin product list/detail/edit pages.
- [x] **Customer management UI (admin-dashboard S14–S16).** customer list with LTV (via
      `AdminUsersBean`), `AdminCustomerDetailBean` + `customer-detail.xhtml`, block/unblock backed
      by `ChangeUserStatusUseCase` with `UserBlockedEvent`/`UserUnblockedEvent` → `AuditLogObserver`.
- [x] **Audit log & dashboard KPIs.** `AuditLogBean` (audit viewer) and `DashboardBean` KPIs
      (totals, new users/orders today, revenue, avg order value, orders by status).
- [x] **product-catalog archive/reactivate.** `ActivateProductUseCase`, `FindProductByIdUseCase`,
      `ListCategoriesUseCase`, `ProductArchivedEvent`, `archive()` in `ProductApplicationService`;
      `manageProduct.xhtml` reworked (506-line diff) with archive/restore actions.
- [x] **Status badges for `RefundStatus`** (APPROVED/PROCESSED/REJECTED CSS on existing tokens) +
      `StatusBadgeCssCoverageTest` now guards all four status enums.
- [x] **Confirm-modal bug fixed.** `confirm-modal.xhtml` moved into `WEB-INF/tags/` (taglib
      `<source>` resolves relative to the taglib — lessons #13); dashboard now includes the tag.
- [x] Housekeeping: standards docs moved under `docs/`, `export.sh` added + translated to English.

## Out of scope / explicit debt

- Refund **approve** transitions PENDING → APPROVED only. The real payment reversal
  (`PaymentGatewayPort.processRefund` → PROCESSED), customer notification emails, and audit-log
  entries for refund actions are future work (no payment/notification provider integration yet).
- Refunds list has no sorting, date-range filter, or customer-name column; reject reason is a
  free-text textarea (no policy-violation dropdown).
- admin-dashboard reporting lane (S20–S23 revenue/product/customer reports + PDF/CSV export),
  admin user management (S25), RBAC/ArchUnit (S26–S27) remain open.
- `PaymentGatewayPort` is a mock adapter (returns success) — same for shipping/notification
  adapters across modules.

## Lessons promoted

- #13 taglib `<source>` paths resolve relative to the taglib file — tag files must live in `WEB-INF/tags/`.
- #14 deterministic aggregate tests: use `reconstitute(id, ...)` (fixed id), not the random-id factory.
- #15 cross-module test classpath uses the installed dependency jar — run the consumer with `-am`.
- #16 changing a state-machine rule breaks pre-existing transition-matrix tests — release gate caught
  a stale `ProductTest` from the archive/reactivate change (ARCHIVED → ACTIVE is legal); fixed before tagging.
