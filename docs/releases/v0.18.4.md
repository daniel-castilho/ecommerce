# Release v0.18.4 — Hardening: guest-cart edge cases + atomic coupon redemption

**Date:** 2026-08-11
**Git tag:** `v0.18.4`
**Baseline commit:** `a05210c` (hardening commit)
**DoD met:** yes (unit + ArchUnit suites green: 292 fast-gate tests, 0 failures; full
`mvn test` on `order-checkout` + `promotions` green incl. Testcontainers ITs; WAR build clean)

## Summary

Hardening pass on the two highest-risk checkout seams. The guest-cart merge can no longer
break a login, and a cart holding a product that was deactivated (or removed) after being
added fails cleanly at checkout instead of ordering stale inventory or surfacing a raw
exception. On the coupon side, `create()` now enforces the validity-window invariant,
`Order.applyCoupon()` refuses a second coupon, and redemption serializes on a pessimistic
write lock so concurrent checkouts can never over-book the usage cap.

## In scope (delivered)

- **Checkout rejects unavailable products** — `OrderApplicationService` now throws
  `CartProductNotAvailableException` when a cart line's product is missing or not `ACTIVE`,
  surfaced to the JSF layer via `CheckoutBean` (clean message, back to payment step). The
  cart is untouched, so the shopper can drop the stale line and re-checkout.
- **Guest-cart merge never fails login** — `GuestCartMergeObserver` retries up to 3 times on
  `CartConcurrentModificationException` (each attempt is a fresh transaction) and swallows +
  logs any other runtime failure before resetting the guest session. Login always succeeds.
- **Coupon window invariant** — `Coupon.create` rejects `validFrom` after `validTo`
  (partial windows still allowed).
- **One coupon per order** — `Order.applyCoupon` throws when a coupon is already applied.
- **Atomic `used_count`** — new `CouponRepositoryPort.findByCodeForUpdate`
  (`PESSIMISTIC_WRITE`); `CouponApplicationService.redeem` reads under the lock so the
  read-modify-write on `used_count` is serialized and the cap can never be exceeded.

## Out of scope / explicit debt

- Concurrency on `used_count` is fixed at the redemption seam, but the counter update is
  still a lock-serialized RMW rather than a single atomic `UPDATE ... SET used_count =
  used_count + 1 WHERE ... < max`; acceptable for MVP volumes, noted for a later batch.
- No cleanup of orphaned guest carts whose merge never completed (e.g. a session that
  logged out before login-time merge). Rows linger; low volume, documented debt.
- Checkout pre-check (`CheckoutBean.getDiscount`) still quotes from the `@PostConstruct`
  `cartView` snapshot, so the live total can diverge by a few cents if a price changed
  between render and submit; the persisted order uses live catalog data.

## How to validate

```bash
# Fast unit/ArchUnit (no Testcontainers):
mvn test -Dtest='*Test' -DfailIfNoTests=false

# Touched modules incl. Testcontainers ITs:
mvn -pl order-checkout,promotions test

# Full build:
mvn clean package -pl web -am
```

Smoke path:

1. Logged-out browser: add a product to the guest cart → log in → the line folds into the
   user cart (quantities summed) and the guest cart row is gone.
2. Checkout with coupon `SAVE10` → order confirmed with the coupon snapshot, cart cleared,
   and `used_count` incremented once.
3. Deactivate the product in admin → add to a guest cart → login → checkout → clean
   "Product is not available" message, no payment attempted, cart intact.

## Lessons promoted

- `docs/lessons.md` #39: a retry loop on an optimistic-lock conflict must live **outside**
  the transactional seam — each `merge()` call is a fresh `@Transactional`, so re-invoking
  the use case from the observer gives a clean persistence context.
- `docs/lessons.md` #40: a read-modify-write on a shared counter (coupon `used_count`) is a
  race no matter how careful the domain logic is; serialize the read with
  `PESSIMISTIC_WRITE` (or use an atomic `UPDATE`) at the port.
