# Release v0.18.0 — Order notifications epic (async transactional outbox)

**Date:** 2026-08-10
**Git tag:** `v0.18.0`
**Baseline commit:** `70480c5` (v0.17.1 — catalog FTS EclipseLink parameter fix)
**DoD met:** yes (each phase smoke-tested end-to-end on the running WAR; unit + ArchUnit + IT
suites green; V27 migration applied to the real DB and registered in flyway history; docs updated)

---

## Summary

Closes the **order notifications epic** across three phases. Checkout now **never touches SMTP**:
an event is claimed as a PENDING row on the delivery log in the business transaction, and a
scheduled poller dispatches the email asynchronously, recording SENT/FAILED. Notifications are
best-effort and at-least-once: a unique idempotency key guards duplicate events, failures are
retried up to 3 attempts and then stop, and a notification preference (or an SMTP outage) never
blocks the order transaction.

- **Phase A** — best-effort email on the request thread (Jakarta Mail), preference-aware,
  never blocking checkout.
- **Phase B** — delivery log (`tb_notification_delivery_log`, V26) with claim-by-idempotency
  (`INSERT … ON CONFLICT DO NOTHING`), SENT/FAILED recording and attempt count.
- **Phase C** — transactional outbox: V27 snapshots `recipient_email`/`subject`/`body` at claim
  time; `OrderNotificationEmailAdapter` enqueues only; `NotificationOutboxProcessor` +
  `NotificationOutboxDispatcher` poll every 5 s on `ManagedScheduledExecutorService` (no EJB).

## In scope (delivered)

- order-checkout `OrderNotificationMessageBuilder` (subjects/bodies for confirmed/shipped +
  refund events) and `OrderNotificationEmailAdapter` (Phase A), later rewritten to **claim-only**
  enqueue (Phase C).
- `NotificationMockAdapter` de-scoped to a test/dev helper (`new`, no CDI scope) so the runtime
  resolves `NotificationPort` to the email adapter.
- V26 `tb_notification_delivery_log` + V27 snapshot columns; `NotificationDelivery` domain model,
  `NotificationDeliveryLogPort` (`claim`, `updateStatus`, `findDue`), JPA entity + repository
  (positional `?N` params, `MAX_ATTEMPTS = 3`).
- `NotificationOutboxProcessor` (`@Transactional`, `findDue(50)` → `Transport.send` → SENT/FAILED,
  never rethrows) and `NotificationOutboxDispatcher` (5 s fixed-delay poll, eagerly started by
  observing `@Initialized(ApplicationScoped.class)`).
- V27 applied to the real Postgres DB and registered in `flyway_schema_history` (rank 27);
  `docs/migrations/V27_rollback.sql` drops the columns.
- Tests: adapter unit tests (claim/skip/disabled), `NotificationOutboxProcessorTest` (SENT/FAILED
  paths via a sender seam), `NotificationDeliveryLogRepositoryIT` (11 cases incl. `findDue`
  boundaries), ArchUnit green.
- Docs: `docs/lessons.md` #31 (best-effort rule), #32 (EclipseLink L2 cache), #33 (CDI lazy),
  README “Current State”, `tasks/order-notifications-phase-c.md` marked DONE.

## Out of scope / explicit debt

- Payment and shipping providers remain mocked (order email is the only real outbound provider).
- No HTML email templates, unsubscribe, or per-channel preferences.
- No DLQ/alerting when attempts are exhausted — exhausted rows stay FAILED in the delivery log
  and are visible only in the audit table + WARNING logs.
- At-least-once window: a crash between `Transport.send` and `markSent` can re-send once (the
  idempotency key guards duplicate events, not the crash window).

## How to validate

```bash
# Fast unit/ArchUnit (no Testcontainers):
mvn test -Dtest='*Test' -DfailIfNoTests=false

# Notification delivery-log IT (Postgres via Testcontainers, drop-and-create):
mvn -pl order-checkout test -Dtest='NotificationDeliveryLogRepositoryIT' -DfailIfNoTests=false

# Full build (final WAR) + run:
mvn -pl web -am install -DskipTests
# stop server, replace dropins/web.war, clear workarea, start
./scripts/run-liberty.sh
```

Smoke path (Open Liberty + Postgres): as a guest, add “QA Test Widget” to the cart, log in as
`qa.admin@loja.com` and check out with coupon `SAVE10` → order is CONFIRMED. In the DB,
`tb_notification_delivery_log` shows the `ORDER_CONFIRMED:{orderId}` row claimed PENDING with
`recipient_email`/`subject`/`body` snapshotted, then flipped FAILED (attempt 2, then 3) by the
background poller within ~5 s ticks; `messages.log` shows the processor WARNING from a
non-request thread. Retries stop at attempt 3.

## Lessons promoted

- `docs/lessons.md` #31: notifications are best-effort — SMTP down must never block checkout
  (verify the commit of the order, not the email).
- `docs/lessons.md` #32: EclipseLink's L2 shared cache serves stale rows after out-of-band SQL —
  restart Liberty after direct stock mutations.
- `docs/lessons.md` #33: CDI is lazy — an unreferenced `@ApplicationScoped` bean never runs;
  start background pollers by observing `@Initialized(ApplicationScoped.class)`.

## Rollback

```bash
git checkout v0.18.0
# or previous tag: git checkout v0.17.1
```

Database: if reverting the runtime, run `docs/migrations/V27_rollback.sql` (drops
`recipient_email`, `subject`, `body` from `tb_notification_delivery_log`) and delete the
`flyway_schema_history` row for version 27. Reverting the code restores synchronous best-effort
sending on the request thread (Phase A behavior) — no outbox, no scheduled poller.
