## Summary

Replaces the manual session-role guard with **real container RBAC**. A Jakarta Security
`IdentityStore` (`UserIdentityStore`, backed by `ValidateCredentialsUseCase`) plus a custom
`LoginAuthenticationMechanism` (`@AutoApplySession`, the Jakarta EE 11 / Security 4.0 flow —
`isAuthenticationRequest()` + `IdentityStoreHandler.validate` + `notifyContainerAboutLogin`)
establish the caller identity; `LoginBean` logs in through `HttpServletRequest.login()`. Admin
URLs (`/user-account/admin/*`, `/product-catalog/manageProduct.xhtml`) are gated by a `web.xml`
ADMIN security-constraint, `@RolesAllowed("ADMIN")`/`SecurityContext.isCallerInRole(...)` resolve
against real groups, and `UserBean` reads login/role state from `SecurityContext` instead of the
manual guard. The page-level `#{userBean.hasRole('ADMIN')}` guard stays as belt-and-braces.

## In scope (delivered)

- [x] `UserIdentityStore` (`jakarta.security.enterprise.identitystore.IdentityStore`, `VALIDATE`
      + `PROVIDE_GROUPS`, priority 10) delegating to `ValidateCredentialsUseCase` — domain rules
      (account status, lockout) stay in the application layer; container groups mirror role names
- [x] `ValidateCredentialsUseCase` port + `UserApplicationService.validateCredentials` /
      `establishSession` (reused by `LoginUseCase.login` via `completeLogin`)
- [x] `LoginAuthenticationMechanism` (`@AutoApplySession`): programmatic login via
      `isAuthenticationRequest()` + `IdentityStoreHandler`; anonymous callers of protected pages
      are redirected to `login.xhtml`
- [x] `LoginBean` switched to `HttpServletRequest.login()` + `changeSessionId()`; failed container
      login renders the inline `FacesMessage` (no container 401)
- [x] `UserBean` now `SecurityContext`-backed (`getCallerPrincipal`/`isCallerInRole`)
- [x] `web.xml`: ADMIN security-constraint for `/user-account/admin/*` and
      `/product-catalog/manageProduct.xhtml`; security-roles `ADMIN`/`CUSTOMER`/`VENDOR`;
      no `<login-config>` (custom mechanism)
- [x] `admin/users.xhtml` keeps a `#{userBean.hasRole('ADMIN')}` guard as belt-and-braces
- [x] Tests: `UserIdentityStoreTest` (VALID / INVALID / NOT_VALIDATED) + 7 new
      `UserApplicationServiceTest` cases (`validateCredentials` x4, `establishSession` x2, +
      pre-existing suite); 46 user-account unit tests green; `web -am test-compile` green

## Lessons promoted

- #8 Jakarta Security 4.0 removed `HttpMessageContext.authenticate(Credential)` — use
  `isAuthenticationRequest()` + `IdentityStoreHandler.validate(...)` +
  `notifyContainerAboutLogin(...)`; `HttpServletRequest.login()` still re-enters the mechanism;
  container groups must match the `security-role` names in `web.xml`.
