**Date:** 2026-08-10
**Git tag:** `v0.18.1`

## Summary

Hardens the Phase A–C notification outbox. FAILED deliveries are now gated behind an
exponential-ish backoff (`next_attempt_at`), the final failure escalates to a new **EXHAUSTED**
terminal status that the poller never touches again, and admins get a **delivery log page** with
manual re-queue for stuck notifications. Also fixes a latent mail-session defect: the configured
mail session was never actually injected (`CWNEN1004E`), and the null-session fallback masked it
with default-session connection errors.

## In scope (delivered)

- **Backoff scheduling** — V28 adds `next_attempt_at`; `NotificationDelivery.backoffDelayFor` is
  30 s after the 1st failure, 2 min after the 2nd, then 5 min; `findDue` returns PENDING rows plus
  FAILED rows below the retry cap whose backoff deadline has passed.
- **EXHAUSTED terminal status** — after `MAX_ATTEMPTS = 3` failures a delivery escalates to
  EXHAUSTED (never polled again), visible in the delivery log for manual resend.
- **Admin delivery log** — `DeliveryLogBean` + `notifications/list.xhtml` list all deliveries
  (optional status filter, newest first) with a "Re-queue" action (`NotificationDeliveryLogPort.resend`)
  that resets a row to PENDING with zero attempts and an open gate.
- **Mail session binding fix** — `server.xml` uses the canonical `jndiName="mail/Session"` and the
  processor + user-account adapter inject via `@Resource(lookup = "mail/Session")`; FROM is resolved
  from the session's `mail.from` (set in server.xml), falling back to `noreply@loja.com`.
- **Migration** — V28 applied to the real DB (backfill keeps existing pending/retryable rows due);
  `docs/migrations/V28_rollback.sql` drops `next_attempt_at`.
- **Tests** — `NotificationDeliveryTest` (backoff math, EXHAUSTED), `NotificationOutboxProcessorTest`
  (SENT/FAILED paths), repository IT expanded to 17 cases (backoff gating, EXHAUSTED,
  `findDeliveries` filter, resend), `DeliveryLogBeanTest`.

## Out of scope / explicit debt

- No DLQ/alerting when attempts are exhausted — EXHAUSTED rows wait in the admin log for a manual
  re-queue.
- Payment and shipping providers remain mocked; no HTML email templates or unsubscribe.
- At-least-once crash window unchanged: a crash between `Transport.send` and `markSent` can
  re-send once.

## How to validate

```bash
# Fast unit/ArchUnit (no Testcontainers):
mvn test -Dtest='*Test' -DfailIfNoTests=false

# Delivery-log IT (Postgres via Testcontainers):
mvn -pl order-checkout test -Dtest='NotificationDeliveryLogRepositoryIT' -DfailIfNoTests=false

# Full build + run:
mvn -pl web -am install -DskipTests
./scripts/run-liberty.sh   # https://localhost:9443/web/
```

Smoke path (proves dispatch + backoff + exhaustion on the running WAR):

1. Place an order, or insert a due PENDING row with app-timezone timestamps:
   `INSERT ... next_attempt_at = now() AT TIME ZONE 'America/New_York'`.
2. Within ~5 s the poller tries SMTP (`localhost:25`, refused) → the row flips FAILED, attempt
   bumped, next attempt gated.
3. Retries fire exactly at the gate (30 s / 2 min) and the final failure marks the row EXHAUSTED
   with attempt 3; `messages.log` shows one WARNING per attempt from a non-request thread.
4. Admin dashboard → "Notification Deliveries" lists the row and "Re-queue" resets it to PENDING.

## Lessons promoted

- `docs/lessons.md` #34: Liberty mail — plain `jndiName` + `@Resource(lookup=...)`, never
  `java:app/env/...` (`CWNEN1004E`); a null Session falls back silently to localhost:25.
- `docs/lessons.md` #35: raw-SQL timestamp inserts must mimic the app's timezone
  (`now() AT TIME ZONE 'America/New_York'`), or rows look 4 h in the future and a healthy poller
  "never picks them up".
