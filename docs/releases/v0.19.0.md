## Summary

Coupons become depth: an admin can now restrict a discount to **specific products** or
**product categories** and cap how many times **one user** may redeem it. The checkout
computes the discount against only the eligible cart lines (live, including the JSF
preview), and redemption records a per-user ledger row so the cap is enforced across
orders. Backwards compatible: existing whole-order coupons keep `ALL` scope with no
targets.

## In scope (delivered)

- **Coupon eligibility scope** — new `CouponScope` (`ALL` / `PRODUCT` / `CATEGORY`) on the
  `Coupon` aggregate with `productIds` / `categoryIds` target sets and
  `isLineEligible(productId, categoryIds)`. `create()` validates the scope contract (no
  targets for `ALL`, product id required for `PRODUCT`, category id required for
  `CATEGORY`), so an invalid combination fails at creation, not at checkout.
- **Per-user redemption cap** — optional `maxUsesPerUser` on the coupon, checked via
  `canBeUsedByUser(usedByUser)`; enforcement is delegated to a persistence ledger so the
  cap holds across the redemption seam.
- **Scope-aware quoting** — `QuoteDiscountUseCase.quote` now takes the cart lines
  (`DiscountLine(productId, categoryIds, lineTotal)`) and discounts only the eligible
  lines; a `CATEGORY`/`PRODUCT` coupon against an ineligible cart quotes zero instead of
  discounting the whole order.
- **Redemption with user identity** — `RecordCouponRedemptionUseCase.redeem(code, userId)`
  counts the user's prior redemptions from the ledger before allowing another use.
- **Persistence** — V29 adds `scope`, `product_ids`, `category_ids`, `max_uses_per_user`
  to `tb_coupon` (CSV storage for targets, scope defaults to `ALL` for existing rows) and
  creates `tb_coupon_redemption` (per-user ledger with a `(coupon_id, user_id,
  redeemed_at)` index). `CouponRepositoryPort` gains `countRedemptionsByUser` /
  `recordRedemption`.
- **Checkout wiring** — `OrderApplicationService` builds `DiscountLine`s from the catalog
  categories it already loads and calls `redeem(code, userId)`; `ProductSnapshot` and
  `CartLineView` now carry `categoryIds` so the `CheckoutBean` live preview honors scope
  too.
- **Admin UI** — create form gains scope selector, product/category CSV inputs and the
  per-user cap (numeric category ids validated); the coupon list shows a Scope column.

## Out of scope / explicit debt

- No admin UI to browse or prune the redemption ledger; it is an audit table only.
- Targets are stored as CSV text columns (`VARCHAR(2000)`) rather than junction tables —
  fine at this scale, revisit if coupons start carrying hundreds of targets or are queried
  by target.
- Per-user cap is enforced on `redeem`, but two concurrent checkouts by the same user are
  serialized by the coupon-row write lock acquired in `redeem` (same mechanism as the
  global cap); a single-user double-tap is therefore safe, but the cap is not enforced at
  the DB constraint level.
- Coupon creation still has no combined "ALL scope + max uses per user" validation conflict
  with targets (the domain rejects it with a clear message); no in-page conditional
  hiding of the CSV fields yet.

```bash
mvn test -Dtest='*Test' -DfailIfNoTests=false

# Full build:

```

Smoke path:

1. Admin → Coupons → New coupon: pick scope `CATEGORY`, category ids `3,7`, per-user cap `2`,
   save; the list shows the Scope column.
2. Cart with a product in category 3 → checkout preview with that code shows the discount;
   add a second, non-eligible product → preview drops to the eligible-line discount only.
3. Redeem the coupon twice with the same account (two orders), then try a third — it is
   refused ("already been used by this user"). A different account can still redeem.
4. Migrate path: coupons created before this release round-trip with `scope = ALL` and no
   targets (existing rows keep whole-order behavior).

## Lessons promoted

- `docs/lessons.md` #41: **when a domain decision needs per-line inputs, thread the raw data
  through the port instead of pre-aggregating to a scalar.** The original `quote(code,
  merchandiseSubtotal)` could not express PRODUCT/CATEGORY scope; switching the port to
  accept cart lines (`DiscountLine`) kept the eligibility rule in the domain
  (`isLineEligible`) and the checkout ignorant of promotion internals. Pre-aggregating
  eligibility in the caller would have leaked scope logic into the wrong module.
- `docs/lessons.md` #42: **an optional per-user cap is best modeled as a count against an
  append-only ledger rather than a counter column.** The global cap is a lock-serialized
  RMW (`used_count`); the per-user cap needs a *user dimension*, so a ledger table with a
  `(coupon_id, user_id)` index and a `COUNT` is simpler and gives an audit trail for free.

## Rollback

```bash
git checkout v0.18.4
```

The V29 migration adds columns and a table with defaults; to roll the schema back, apply a
plain revert (drop the four columns, drop `tb_coupon_redemption`), then reset the source.
